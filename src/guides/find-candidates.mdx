Discovery in ClearedStack v3.1 is handled by `cs-01-intake`, the first of ten **100% deterministic** Go workers running in the `cs-workers` Kubernetes namespace. Zero AI models run during intake: given the same URL or submission, `cs-01-intake` produces the exact same output on any cluster, with zero token cost.

Its job is to collect public federal-contracting tools, spreadsheets, calculators, and community suggestions, clean their web addresses, check for duplicates, and assign a persistent `PA-XXXX` tracking identifier before handing the record to `cs-02-observe`.

## Deterministic URL normalization

Websites often serve the same tool at slightly different addresses—with tracking tags, uppercase letters, or trailing slashes. Before saving anything, `cs-01-intake` runs every incoming link through fixed, repeatable normalization rules:

- **Scheme and host casing:** Converts the scheme (`https`) and domain name to lowercase.
- **Tracking and session removal:** Strips marketing query parameters (`utm_*`, `ref`, `fbclid`, `gclid`), session identifiers, and URL `#` fragments.
- **Path cleanup:** Removes redundant trailing slashes and default index filenames where appropriate so equivalent paths resolve to one canonical address.
- **Public-only boundary check:** Rejects non-public schemes, internal network addresses, or links that require credentials or paywall bypass.

Because normalization is pure Go code with golden test fixtures, two people submitting the same tool with different referral links always produce the exact same canonical URL.

## SHA-256 deduplication and PA-XXXX assignment

Once a URL is normalized, `cs-01-intake` computes its **SHA-256** cryptographic hash and checks it against `hub-queue-api` and Postgres (`core.*` tables) in the `clearedstack` control-plane namespace:

1. **Duplicate hash found:** If the SHA-256 digest already matches an existing record or known alias, `cs-01-intake` does not create a duplicate. It logs the sighting against the existing `PA-XXXX` entry (or links it as a mirror) and stops.
2. **New canonical URL:** If the hash is new, `cs-01-intake` mints a persistent `PA-XXXX` identifier (such as `PA-0001`), records the intake source, and queues the item for `cs-02-observe` via `hub-queue-api`.

Every state change is immediately visible through read-only `pub.*` Postgres views on the `/guides/workflow-state-machine/` page of `clearedstack.com`.

## Four deterministic sub-tools

Candidate links arrive from very different places—government portals, GitHub issues, scheduled web sweeps, and the Portal submission form. Instead of using an AI model to interpret unfamiliar formats, `cs-01-intake` routes each source through a dedicated sub-tool inside its own repository under `tools/<case>/` (registered in `tools/registry.yaml`, each with `match.yaml`, deterministic Go logic, and golden test fixtures).

| Sub-tool (`tools/<case>/`) | Source | Deterministic job |
| --- | --- | --- |
| `sam-gov` | SAM.gov public notices | Extracts public tool links, agency calculators, and attachment URLs from SAM.gov feeds. |
| `github-issues` | GitHub public mirror | Parses structured tool and paperwork suggestions opened on the public GitHub repository. |
| `web-sweep` | Public `.gov`, `.mil`, APEX, and vendor sites | Runs scheduled, `robots.txt`-respecting sweeps across public contracting resources. |
| `site-form` | `clearedstack.com` Portal | Validates and normalizes direct candidate submissions and `✎` intake proposals from visitors. |

If `cs-01-intake` encounters a new source format that none of its sub-tools recognize, it **fails closed**: it pauses that item in `needs_subtool`, and `cs-10-notify` opens a task in the `cs-01-intake` repository. Once a new sub-tool and golden fixture are committed, `cs-runner` builds the updated worker with `ko` (no Docker), `cs-store` deploys it, and `hub-queue-api` automatically replays every paused item.

## Anonymous no-login submissions

ClearedStack has no login lock. Any visitor can submit a candidate tool or propose an intake edit (`✎`) on `clearedstack.com` without creating an account or signing in.

To keep the queue clean without CAPTCHAs or user accounts, `site-form` and Portal `✎` submissions pass through a five-layer deterministic shield:

1. **Browser Proof-of-Work:** A roughly one-second SHA-256 puzzle solved in the visitor's browser on submit stops automated bot floods.
2. **Honeypot field:** A hidden form field silently discards automated scraper submissions.
3. **Daily-salted IP hash rate limit:** Limits repeated submissions per hashed IP without ever storing raw visitor IP addresses.
4. **Strict schema validation:** Checks the submission against `ownership_map.json`, caps payload size at 4 KB, and strips all HTML and scripts.
5. **Owner gate (`cs-04-decide`):** Community proposals sit in `core.edit_proposal` (`pending_approval`) and never touch `cs-git` or the cluster until the owner clicks **Approve** in `/guides/ownership-map-and-edit-loop/`.

Visitors see their submission's progress live on the Portal as a status pill: **Proposed -> Approved -> Building -> Live**.

## What intake never does

Discovery and intake remain strictly passive and public. `cs-01-intake` never creates accounts on third-party sites, requests sales demos, bypasses paywalls or CAPTCHAs, ignores `robots.txt`, or accepts Controlled Unclassified Information (CUI) or proprietary bid figures.
