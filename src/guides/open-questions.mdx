## What is decided in v3.1

The following architectural, licensing, and operational decisions are final for ClearedStack v3.1.

### 10 deterministic worker repositories

Zero AI runs at runtime anywhere in the pipeline or in any shipped compliance tool. All pipeline work is executed by 10 deterministic Go worker repositories (`cs-01-intake` through `cs-10-notify`) that produce identical output on any cluster.

| Worker repo | Deterministic responsibility | Edge-case handling |
| --- | --- | --- |
| `cs-01-intake` | Normalize URLs, SHA-256 deduplicate, assign `PA-XXXX`. | Sub-tools in `tools/<case>/` |
| `cs-02-observe` | Fetch public pages and run DOM/PDF extractors into strict JSON behind a clean-room wall. | Tiny ~30 MiB HTTP Go pods; spawns on-demand headless browser `Job` pods only for JS-heavy sites |
| `cs-03-evaluate` | Run YAML/Go rule engine for 5 knockout gates, 100-point rubric, and 5 tie-breakers. | Category rubric profiles in `tools/<case>/` |
| `cs-04-decide` | Owner-only decision inbox on the Portal for item determinations and edit approvals. | Human gate only |
| `cs-05-provenance` | Stamp provenance notes via Go templates, enforce 48h/5d SLAs, and compile clean-room JSON specs. | Spec profiles in `tools/<case>/` |
| `cs-06-build` | Generate isolated static tool repos from clean-room specs and worked-example fixtures. | Deterministic stack templates |
| `cs-07-verify` | Run 5-condition test suite (offline execution, `connect-src 'self'`, zero tracking, worked-example parity). | Deterministic pass/fail gate |
| `cs-08-catalog` | Publish verified, linked, merged, or retired entries to the `clearedstack.com` catalog. | Deterministic catalog sync |
| `cs-09-monitor` | Scheduled ETag, XML, and DOM diff checks on FAR/DFARS/NIST, live tools, and linked tools. | Source watchers in `tools/<case>/` |
| `cs-10-notify` | Route approved Portal edits, `needs_subtool` tasks, and fingerprinted errors into `cs-git` and owner alerts. | Notification targets in `tools/<case>/` |

When a worker encounters an unfamiliar page layout or format, it fails closed into `needs_subtool`, opens a task in the owning worker repository, and automatically replays queued items once a new deterministic sub-tool and golden fixture are merged.

### MIT clean-room Go microservices (no Forgejo, Argo CD, CasaOS, or Docker)

Rather than bundling heavy third-party platforms with mixed licenses or upstream operational overhead, ClearedStack v3.1 runs custom clean-room Go microservices licensed under **MIT** across all repositories (`clearedstack.com`, `cs-01` through `cs-10`, `cs-git`, `cs-registry`, `cs-runner`, and `cs-store`). Inspiration is drawn from Forgejo, Argo CD, and CasaOS workflows, with zero copied upstream code.

| Replaced component | v3.1 clean-room replacement | Role in platform |
| --- | --- | --- |
| **Forgejo** | `cs-git` | Internal bare `.git` server on a PVC with Smart HTTP/SSH, webhooks, and outbound push-mirroring to GitHub on change. |
| **GHCR / Harbor** | `cs-registry` | Internal-only OCI v2 registry on a PVC retaining the last 5 digests per app for instant rollback. |
| **Forgejo Actions & Docker** | `cs-runner` | Ephemeral Kubernetes build Jobs using `ko` for Go and rootless BuildKit for Next.js—zero Docker anywhere, running on `k3s` and `containerd`. |
| **Argo CD + CasaOS** | `cs-store` | App-store reconciler reading `app.yaml` from `cs-git` for 1-click Install, Upgrade, Pause, and Rollback via Kubernetes Server-Side Apply. |
| **GitHub as primary host** | Public code mirror only | `cs-git` pushes code changes to GitHub for public visibility; zero container images are ever stored on GitHub. |

### Two Kubernetes namespaces

The entire 17-pod platform fits on a single 4 GiB `k3s` node and is isolated into **2 namespaces**:

- **`clearedstack` (control plane):** Runs `clearedstack-web`, `hub-queue-api`, `postgres`, `cs-git`, `cs-registry`, `cs-runner`, and `cs-store`.
- **`cs-workers` (pipeline workers):** Runs all 10 deterministic worker deployments (`cs-01-intake` through `cs-10-notify`) and on-demand browser Jobs.

### Open no-login public sandbox

Everything running and being developed is shown publicly and for free with **no login lock** on `clearedstack.com`. Any visitor can use the Portal, inspect live worker health and queues, read sanitized error codes (`E_TIMEOUT`, `E_PARSE`, `E_NEEDS_SUBTOOL`), and propose edits via `✎` buttons without creating an account.

Openness is paired with deterministic guardrails so public access never exposes cluster internals or host safety:

- **Network isolation:** Only `clearedstack-web` has a public Ingress; internal IPs, `.svc.cluster.local` DNS names, node names, `NetworkPolicy` rules, and credentials stay cluster-private, and the Portal reads only sanitized `pub.*` Postgres views.
- **Five-layer edit shield:** Anonymous `✎` proposals pass a ~1-second browser Proof-of-Work puzzle, a honeypot field, a daily-salted IP hash rate limit, strict 4 KB schema validation against `ownership_map.json`, and a mandatory human approval gate in `cs-04-decide` before touching `cs-git`.
- **Safe failure and rollback:** If a public interaction triggers an unexpected edge case or breaks a view, the sanitized error is logged visibly to help improve the system while `cs-store` preserves instant rollback across the last 5 signed OCI digests.

## What remains open

While the v3.1 runtime and sandbox architecture are settled, three areas remain open for further design and community input.

| Open area | Core question | Current working default | Why it remains open |
| --- | --- | --- | --- |
| **Dataset licensing edge cases** | How should MIT code licensing interact with CC0 1.0 public-domain records when third-party excerpts, worked-example government tables, or vendor-submitted errata are compiled into `clearedstack.com` and `cs-05-provenance` specs? | MIT across all code repositories; clean-room factual extraction for regulatory and vendor observations. | Edge cases around mixed-provenance JSON bundles, statutory tables with agency formatting, and user-proposed edit contributions need explicit legal clarity before external dataset mirrors proliferate. |
| **Multi-node federation** | How should independent ClearedStack v3.1 instances synchronize `cs-git` repositories, `hub-queue-api` work items, or `cs-registry` digests if the project grows beyond a single `k3s` node or organizations self-host their own mirrors? | Single-node `k3s` deployment with outbound GitHub code mirroring from `cs-git`. | Federation introduces hard distributed-systems trade-offs around deterministic replay, conflicting `PA-XXXX` IDs, and trust boundaries between independent `cs-04-decide` owner queues. |
| **Community stewardship** | When and how should the project transition from a single-owner Phase 1 operation to a durable multi-maintainer model (legal entity, backup owner-mode access, and shared `cs-04-decide` review)? | Single human owner with an inviolable zero-revenue policy and public git history. | Sustaining a zero-revenue public-interest compliance platform long-term requires clear succession rules, co-maintainer ethics attestations, and a governance structure that cannot be captured by commercial vendors. |
