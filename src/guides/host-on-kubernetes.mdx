ClearedStack runs as a complete, self-contained platform on a single lightweight Kubernetes cluster using **k3s** and **containerd**. You do not need Docker installed on your server, in your build pipeline, or anywhere on your cluster.

The entire 17-pod platform—7 control-plane services and 10 deterministic workers—requests roughly **640 MiB of RAM** for the control plane (with a 1.25 GiB limit) and about **300 MiB** for all 10 workers combined. That means the whole stack fits comfortably on a single 4 GiB cloud server costing $10 to $20 per month.

## Why Docker is completely removed

Traditional setups rely on the Docker daemon to build and run containers, which adds unnecessary memory overhead and security risk inside Kubernetes. ClearedStack removes Docker at every stage:

- **Direct runtime with containerd:** Kubernetes already includes `containerd`, a minimal container runtime that starts and manages pods directly. Running a separate Docker daemon on the host wastes memory and adds an extra layer to maintain.
- **No Docker-in-Docker builds:** Building images inside a cluster with Docker usually requires mounting the host Docker socket or running privileged containers, both of which give build jobs near-root control over the server. ClearedStack replaces that with **ko** (which compiles Go services straight into minimal container images) and **rootless BuildKit** (which builds the Next.js web portal without elevated privileges).
- **No public image registries:** ClearedStack never pushes container images to Docker Hub or GitHub. Source code is mirrored to GitHub for public visibility, while all built container images stay inside your cluster's own private registry.

## Two-namespace layout

ClearedStack divides the cluster into two **namespaces** (isolated virtual folders inside Kubernetes) so the control plane and the automated workers stay cleanly separated:

| Namespace | What lives here | Purpose |
| --- | --- | --- |
| `clearedstack` | 7 control-plane pods | Runs the public web portal, queue API, PostgreSQL database, Git server, image registry, build runner, and app-store reconciler |
| `cs-workers` | 10 deterministic workers (`cs-01` through `cs-10`) | Executes the 10-stage pipeline with zero AI at runtime; `cs-02-observe` also spawns temporary headless browser jobs only when a page requires JavaScript |

Network policies ensure that only the web portal (`clearedstack-web`) accepts traffic from the public internet. Internal IP addresses, database credentials, and cluster hostnames never leave the cluster.

## The control plane (~640 MiB RAM)

Instead of bundling heavy third-party suites like Forgejo, Harbor, or Argo CD, ClearedStack uses four small, purpose-built Go microservices alongside the web portal and database. Each microservice does one job and keeps memory use predictable:

| Component | Replaces | What it does | Requested RAM |
| --- | --- | --- | --- |
| `cs-git` | Forgejo | Stores bare Git repositories on a persistent volume, triggers build webhooks on push, and mirrors public code commits to GitHub | 64 MiB |
| `cs-registry` | Harbor / GHCR | Stores OCI container images privately inside the cluster, keeps the last five versions per app for instant rollback, and cleans up old layers daily | 64 MiB |
| `cs-runner` | Forgejo Actions | Listens for `cs-git` push webhooks, launches short-lived `ko` or rootless BuildKit jobs without Docker, runs tests, signs images, and updates app manifests | 32 MiB |
| `cs-store` | Argo CD + CasaOS | Reads app manifests from `cs-git`, deploys updates with built-in Kubernetes Server-Side Apply, and reports sanitized pod health back to the portal | 48 MiB |
| `clearedstack-web`, `hub-queue-api`, `postgres` | Portal + Hub API + DB | Serves the public ink-on-paper portal, live pipeline views, anonymous edit proposals, and the PostgreSQL 17 database | 432 MiB |

## How updates flow without Docker

When a change lands in `cs-git`—either from you or from an approved public edit—`cs-git` sends a webhook to `cs-runner` and mirrors the code commit to GitHub. `cs-runner` spins up a temporary, unprivileged Kubernetes job that builds the new image with `ko` or rootless BuildKit, signs it, and pushes it to `cs-registry`.

Once the image is stored, `cs-runner` records the new image digest in the app's manifest inside `cs-git`. `cs-store` notices the updated manifest, rolls out the new pods one at a time in the `clearedstack` or `cs-workers` namespace, and streams the live status to the portal. If anything looks wrong, `cs-store` can roll back to any of the last five digests held in `cs-registry` with a single click.
