Earlier versions of this guide described a ten-stage pipeline as an unbuilt plan. In ClearedStack v3.1, that essay is now running software: ten separate, MIT-licensed Go repositories (`cs-01-intake` through `cs-10-notify`) that discover existing government-contracting tools, check them against public rules, build clean-room browser alternatives, and keep the live catalog up to date.

Every worker in the engine is **100% deterministic**—meaning there is zero AI at runtime, no language-model token cost, and no guesswork. Given the same input, each worker produces the exact same output on any cluster.

## From ten stages on paper to ten live repositories

All ten workers run inside the `cs-workers` Kubernetes namespace. Each repository owns one clear job in the assembly line, and workers that face varied websites or document formats use `tools/<case>/` sub-tools—small, permanent rule modules with golden test fixtures—to handle edge cases without AI.

| Worker Repo | What it does (100% deterministic) | Sub-tools (`tools/<case>/`) |
| --- | --- | --- |
| `cs-01-intake` | Normalizes submitted or discovered URLs, deduplicates via SHA-256, and assigns a `PA-XXXX` ID. | Yes (`sam-gov`, `github-issues`, `web-sweep`, `site-form`) |
| `cs-02-observe` | Fetches public pages as tiny ~30 MiB Go HTTP pods (spawning on-demand headless browser `Job` pods only for JS-heavy sites), extracts inputs/outputs into JSON, and seals raw snapshots behind the clean-room wall. | Yes (`saas-marketing`, `gov-portal`, `agency-pdf`, `<vendor-slug>`) |
| `cs-03-evaluate` | Runs the YAML/Go rule engine for the five knockout gates, the 100-point rubric, and five tie-breakers. | Yes (`rubric-profiles/<category>`) |
| `cs-04-decide` | Powers the owner-only decision inbox on the Portal (Approve, Link, Merge, Park, Reject, Override, and public edit approvals). | No |
| `cs-05-provenance` | Stamps provenance notes with Go templates, enforces 48-hour identity verification and 5-day opt-out SLAs, and compiles clean-room JSON build specs. | Yes (`spec-profiles/<tool-type>`) |
| `cs-06-build` | Generates an isolated static tool repository from the clean-room spec and worked-example fixtures. | Yes (`stack-templates/calculator`, `checklist`, `validator`, `decision-tree`) |
| `cs-07-verify` | Runs the five-condition verification suite (offline operation, `connect-src 'self'`, zero tracking, worked-example assertions). | No |
| `cs-08-catalog` | Publishes verified, linked, merged, or retired entries to the live `clearedstack.com` catalog. | No |
| `cs-09-monitor` | Runs scheduled ETag, XML, and DOM diff checks on FAR/DFARS/NIST rules, live tools, linked tools, and parked blockers. | Yes (`federal-register`, `ecfr`, `nist-csrc`, `linked-tool-watch`, `live-catalog`) |
| `cs-10-notify` | Routes approved Portal edits, `needs_subtool` tasks, and fingerprinted errors into `cs-git`, and sends owner alerts. | Yes (`internal-git`, `github-mirror`, `webhook-alert`, `portal-sse`) |

When a worker encounters an unfamiliar page layout or document format, it **fails closed**: it pauses that item in `needs_subtool`, and `cs-10-notify` opens a task in the owning repository. Once a new deterministic sub-tool and golden test are added, `cs-runner` builds the updated worker image with `ko` (zero Docker anywhere), `cs-store` rolls it out, and `hub-queue-api` automatically replays every paused item.

## How hub-queue-api and Postgres coordinate the line

Workers never talk directly to each other or touch the database themselves. Instead, `hub-queue-api` and Postgres 17 sit in the `clearedstack` control-plane namespace and act as the central dispatcher:

- **Lease-based queues:** Each worker polls `hub-queue-api` over internal ServiceAccount HTTP to claim a time-limited lease on its next item, then writes back the result or a sanitized error code (`E_TIMEOUT`, `E_PARSE`, `E_NEEDS_SUBTOOL`).
- **Clean-room separation:** Raw HTML or vendor snapshots captured by `cs-02-observe` stay sealed behind the clean-room boundary; downstream build workers (`cs-06-build`) only read sanitized JSON specs derived from public regulations.
- **Public mirror without cluster exposure:** Code changes live in `cs-git` and mirror outward to GitHub on change, while internal IPs, tokens, and cluster topology stay private inside the control plane.

## Feeding the live Portal

The public Portal (`clearedstack-web`) reads sanitized `pub.*` Postgres views and live Server-Sent Events (SSE) from `hub-queue-api`. There is no login lock: any visitor can watch the engine run, inspect errors, or propose an edit (`✎`) that enters `cs-04-decide` for owner approval.

| Portal Route | What the 10-worker engine feeds into it |
| --- | --- |
| `/guides/workflow-state-machine/` | Live queue depths, active worker health, item trails from `PA-XXXX` intake to catalog, and compact `[Why?]` rule drawers replacing long static essays. |
| `/guides/ownership-map-and-edit-loop/` | The `cs-04-decide` owner inbox for pending tool determinations and anonymous public edit proposals. |
| `/tools/` | The finished, verified client-side tools published by `cs-08-catalog`, plus all 17 platform and worker apps (`#apps`). |
