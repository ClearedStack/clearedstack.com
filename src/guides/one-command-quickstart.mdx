ClearedStack is designed so anyone can run the entire platform on a single modest server. You do not need a large cloud cluster, a managed Kubernetes service, or a paid container registry. All 17 pods—the public Portal, the internal Git server, the image builder, the private container registry, the app-store reconciler, the database, and all 10 deterministic workers—fit comfortably on a single 4 GiB `k3s` node costing roughly $10 to $20 per month.

## One Node, Two Namespaces, Seventeen Pods

Traditional self-hosted platforms often bundle heavy third-party suites that demand 8 GiB to 16 GiB of memory just to sit idle. ClearedStack replaces those suites with small, single-purpose Go services and runs everything inside two isolated Kubernetes namespaces using `k3s` and `containerd`, with no Docker anywhere.

| Namespace | Pods | Role | Typical Memory |
| --- | --- | --- | --- |
| `clearedstack` | 7 control-plane pods | Public Portal (`clearedstack-web`), queue API (`hub-queue-api`), Postgres 17, internal Git (`cs-git`), internal registry (`cs-registry`), image builder (`cs-runner`), and app-store reconciler (`cs-store`) | ~640 MiB requested (~1.25 GiB limit) |
| `cs-workers` | 10 worker pods | Deterministic pipeline workers (`cs-01-intake` through `cs-10-notify`) with zero AI at runtime | ~300 MiB total |

Because the entire stack requests under 1 GiB of memory at rest, a 4 GiB virtual private server or home mini-PC leaves plenty of headroom for the operating system, Postgres storage, ephemeral build jobs, and occasional on-demand headless browser jobs spawned by `cs-02-observe` for JavaScript-heavy websites.

## What the One-Time Setup Job Initializes

Deploying your own instance requires only a single quickstart manifest apply to a fresh `k3s` cluster. As soon as the manifest lands, a one-time setup job runs automatically to wire the platform together from scratch so you do not have to configure databases, registries, or secrets by hand.

| Setup Step | What Happens Automatically | Why It Matters |
| --- | --- | --- |
| Cluster-private secrets | Generates database passwords, service-account tokens, `cosign` image-signing keys, and the daily IP-hashing salt | Credentials never touch Git and stay inside your cluster |
| Database bootstrap | Initializes Postgres 17 with internal `core` tables and read-only `pub` views | Separates private operational data from what the public Portal displays |
| Internal Git seeding | Creates bare repositories in `cs-git` for the Portal, control-plane services, and all 10 workers with starter `app.yaml` files | Gives your cluster its own self-contained source of truth |
| Local image builds | Triggers `cs-runner` to compile Go services with `ko` and the Next.js Portal with rootless BuildKit, then signs and pushes them to `cs-registry` | Eliminates Docker and avoids pulling prebuilt images from external registries |
| Network boundaries | Applies network policy rules so only `clearedstack-web` accepts public traffic | Keeps internal IPs, the database, Git, registry, and workers unreachable from the internet |

Once the setup job finishes, `cs-store` reconciles the `app.yaml` manifests and brings up all 17 pods. From there, you can open the Portal, watch the live pipeline, and manage upgrades or rollbacks directly from the built-in App Store view.

## Clean-Room MIT Licensing and Easy Forking

Every ClearedStack repository—the Portal, the four control-plane microservices, and all ten workers—is released under the **MIT License**. Although the architecture takes inspiration from tools like Forgejo, Argo CD, and CasaOS, every line of Go code is written from scratch in a clean room with zero copied upstream code and zero copyleft obligations.

That clean-room MIT foundation makes it straightforward to fork ClearedStack for your own organization, agency, or research project:

- **Customize without permission or fees:** You can rebrand the Portal, change evaluation rubric weights, or run a private instance internally without licensing restrictions.
- **Add deterministic edge-case handlers:** Each worker supports modular sub-tools under its own `tools` directory. When you add a new parser or rule with a golden test fixture, your cluster's `cs-runner` automatically tests, builds, signs, and rolls out the updated worker.
- **Control your public mirror:** By default, `cs-git` mirrors code commits to GitHub on change while keeping container images strictly inside your cluster. When you fork the project, you simply point `cs-git` at your own repository mirror—or leave mirroring off for a completely self-contained deployment.

The result is a small, transparent platform you can stand up in minutes, inspect line by line, and adapt to your own workflow for the price of a basic VPS.
