## Overview & Role

`cs-store` (`v0.1.0-draft`, owned by the `cs-store` repository) is a clean-room MIT Go microservice running in the `clearedstack` control-plane namespace. It combines GitOps deployment reconciliation with an App Store lifecycle controller—replacing both Argo CD and CasaOS with a single binary that speaks native Kubernetes **Server-Side Apply** and introduces **zero custom CRDs**.

`cs-store` watches `app.yaml` manifests in `cs-git` and signed digests in `cs-registry`, reconciles all 17 platform workloads across `clearedstack` (7 control-plane pods) and `cs-workers` (10 deterministic worker pods), and streams sanitized pod health and error codes to `hub-queue-api` for display on `/tools/#apps` and `/guides/live-command-portal/`.

## Interfaces & Data Contracts

`cs-store` bridges Git state, OCI digests, Kubernetes workloads, and public Portal telemetry:

- **Desired State (`cs-git` + `cs-registry`):** Reads `app.yaml` definitions from `cs-git` and verifies corresponding `sha256` digests in `cs-registry` (up to 5 retained versions per app).
- **Cluster Reconciliation (Kubernetes API):** Applies `Deployment`, `Service`, and `NetworkPolicy` manifests via Server-Side Apply across `clearedstack` and `cs-workers`.
- **1-Click App Store Actions (`/tools/#apps` via `hub-queue-api`):**
  - **Install:** Applies an app's manifests into its target namespace for the first time.
  - **Upgrade:** Rolls the Deployment forward to the latest signed digest built by `cs-runner`.
  - **Pause:** Scales the workload down cleanly without deleting its configuration, PVC, or queue state.
  - **Rollback:** Switches `app.yaml` and the live Deployment back to one of the previous 5 signed digests retained in `cs-registry`.
- **Sanitized Telemetry (`cs-store` -> `hub-queue-api`):** Watches Kubernetes `Pod`, `Deployment`, and `Event` objects, strips internal metadata, and emits normalized health states (`healthy`, `idle`, `degraded`, `paused`) and standardized error codes (`E_TIMEOUT`, `E_PARSE`, `E_NEEDS_SUBTOOL`).

## Sub-Tools & Failure Modes

`cs-store` is a control-plane reconciler and does not host `tools/<case>/` deterministic sub-tools (`subTools: []`).

| Failure Mode | Trigger | System Behavior & Recovery |
| --- | --- | --- |
| **Pod crash or failed health check** | New rollout fails readiness or exits non-zero | Surfaces as `P0 · Critical` (`--danger`) on Command and `/tools/#apps` with 1-click **Rollback** to a prior `cs-registry` digest. |
| **Server-Side Apply conflict** | Manual out-of-band edit collides with `cs-store` field ownership | Reconciliation logs the conflict cleanly without silently overwriting unrelated cluster state. |
| **Missing or unsigned digest** | `app.yaml` references a digest absent from `cs-registry` | Deployment rollout is blocked; `cs-store` preserves the currently running healthy replica set. |
| **Hub API unreachable** | `hub-queue-api` restarts during a status update | `cs-store` continues reconciling Kubernetes workloads independently and retries telemetry delivery once `hub-queue-api` recovers. |

## Security & Clean-Room Boundaries

- **Strict topology sanitization:** Before forwarding any pod status or Kubernetes event to `hub-queue-api` (and ultimately `pub.*` views), `cs-store` strips all internal cluster IP addresses, node names, pod hostnames, and internal cluster DNS names. Public visitors see only sanitized health states and standardized error codes.
- **No public Ingress:** `cs-store` is strictly cluster-private; owner lifecycle actions are authenticated and routed through `hub-queue-api`.
- **Least-privilege RBAC & non-root:** Runs as an unprivileged non-root user with dropped Linux capabilities and scoped Kubernetes RBAC limited to managing platform workloads in `clearedstack` and `cs-workers`.
