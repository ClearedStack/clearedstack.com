ClearedStack is built to operate without an internet connection. Everything the platform needs to host code, build container images, store data, and run deterministic tools lives inside the platform itself, with no Docker anywhere and no runtime calls to outside AI services or third-party trackers.

When you move ClearedStack onto a closed or air-gapped network, you choose between two modes: running the **full self-contained Kubernetes stack** inside a disconnected enclave, or exporting a **Snapshot Mode** bundle for single-file offline use.

## Choose your closed-network mode

| Mode | What runs inside | Best for | Updates and edits |
| --- | --- | --- | --- |
| **Full Enclave Stack** | Complete 17-pod Kubernetes platform (`clearedstack` and `cs-workers` namespaces) on `k3s` and `containerd` | Teams that want the live Portal, internal code hosting, in-cluster builds, and all 10 deterministic workers inside an enclave | Users can propose edits, build with `cs-runner`, and deploy via `cs-store` completely offline |
| **Snapshot Mode** | A single frozen, timestamped static bundle (HTML, CSS, JavaScript, fonts, and verified tools) | Analysts or small teams who only need to read guides, search the catalog, and run tools in a browser without a cluster | Read-only and fixed at the export timestamp; refresh by carrying in a newer snapshot |

## Mode 1: Full self-contained Kubernetes stack

Because ClearedStack does not depend on GitHub for container images or external registries at runtime, the entire platform can live inside a disconnected enclave with zero internet access.

The stack runs on `k3s` with `containerd`—no Docker daemon is installed or used anywhere. Go services are built with `ko`, and the Next.js Portal is built with rootless BuildKit. Inside the cluster, two namespaces keep responsibilities separate:

- **The `clearedstack` namespace (control plane):** Runs the seven core services—`clearedstack-web` (the Portal and App Store interface), `hub-queue-api` (queues and proposals), Postgres 17 (database storage), `cs-git` (internal Git repositories), `cs-registry` (internal OCI container image store), `cs-runner` (in-cluster builder and test runner), and `cs-store` (app reconciler and health monitor).
- **The `cs-workers` namespace (workers):** Runs the 10 deterministic workers (`cs-01-intake` through `cs-10-notify`). Each worker runs predictable, rule-based Go code with zero AI at runtime. For JavaScript-heavy pages, `cs-02-observe` spawns on-demand headless browser jobs only when needed.

Inside an enclave, `cs-git`, `cs-registry`, `cs-runner`, and `cs-store` form a closed loop. Teams can review proposals in the Portal, commit changes to `cs-git`, build and sign new images with `cs-runner`, push them to `cs-registry`, and roll them out with `cs-store` without ever touching the public internet.

### What changes when disconnected

| Component | Connected behavior | Disconnected enclave behavior |
| --- | --- | --- |
| **`cs-git`** | Mirrors `main` and tags outbound to GitHub | Outbound GitHub mirror is disabled; all code stays in local bare repositories |
| **`cs-09-monitor`** | Checks public regulatory feeds (such as eCFR and NIST) on a schedule | External fetches are paused or pointed at internal enclave mirrors |
| **`cs-02-observe`** | Fetches public candidate pages over HTTPS | Only fetches addresses reachable inside your enclave, or processes imported local bundles |
| **`cs-registry`** | Stores signed OCI images built by `cs-runner` | Serves all cluster images locally via `containerd` with zero external pulls |

## Mode 2: Snapshot Mode for single-file offline users

Not every closed-network user needs a Kubernetes cluster, a Postgres database, or background workers. **Snapshot Mode** exports a frozen, timestamped static bundle containing the site, the guides, the tool catalog, and every verified client-side tool.

You can open a Snapshot Mode bundle directly from a local folder or serve it from any plain internal web server. Every font, stylesheet, script, and calculation runs locally in the visitor’s browser, and strict Content Security Policy rules (`connect-src 'self'`) prevent any outside network request.

Because Snapshot Mode has no backend cluster, interactive control-plane features—such as submitting new proposals, running the 10-worker pipeline, or viewing live `cs-09-monitor` checks—are turned off. The bundle carries a visible build timestamp so users always know the exact date of the catalog and regulatory rules they are reading.

## Moving files across the air gap

Both modes follow the same transfer discipline: package on a connected machine, record a SHA-256 fingerprint before the move, carry the bundle through your organization’s approved transfer process, and verify the fingerprint on arrival before loading anything.

| Transfer item | Used for | What it contains |
| --- | --- | --- |
| **Enclave bundle** | Mode 1 (Full Enclave Stack) | Signed OCI image archives exported for `containerd` and `cs-registry`, Kubernetes manifests, and `cs-git` repository bundles |
| **Snapshot archive** | Mode 2 (Snapshot Mode) | One compressed, timestamped static bundle ready to extract or open offline |
| **SHA-256 checksum file** | Both modes | The cryptographic fingerprint used on the inside to prove not a single byte changed in transit |

If a checksum does not match on the closed side, discard the transfer and move a fresh copy. Before relying on any regulatory threshold or compliance rule inside a disconnected environment, compare the snapshot or enclave sync date against the effective date of the rule you are checking.
