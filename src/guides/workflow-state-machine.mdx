ClearedStack v3.1 turns the original ten-stage prior-art workflow from a static set of essays into a live, 100% deterministic pipeline. Ten small Go services (`cs-01-intake` through `cs-10-notify`) run in the `cs-workers` Kubernetes namespace and pull leased work from `hub-queue-api`. There is zero AI at runtime: every step uses repeatable rules, templates, and sub-tools so the same inputs always produce the same outputs.

## From 10 website stages to 10 worker repositories

The original website described ten conceptual stages from discovery to monthly revisit. In v3.1, some stages were combined into a single worker, automated quality checks were split into their own worker, and a tenth worker was added to close notification and code-change loops.

| Worker repo | Replaces old stage(s) | Deterministic job | Sub-tools (`tools/<case>/`) |
|---|---|---|---|
| `cs-01-intake` | Stage 1 (Discover) + Stage 2 (Record) | Normalize URLs, deduplicate by SHA-256, and assign `PA-XXXX` IDs. | Yes (`sam-gov`, `github-issues`, `web-sweep`, `site-form`) |
| `cs-02-observe` | Stage 3 (Observe) | Fetch public pages via Go extractors (or on-demand headless browser jobs for JS-heavy sites) and seal raw captures behind the clean-room wall. | Yes (`saas-marketing`, `gov-portal`, `agency-pdf`, `<vendor-slug>`) |
| `cs-03-evaluate` | Stage 4 (Screen) + Stage 5 (Score) | Run 5 binary knockout gates, the 100-point rubric, and 5 tie-breakers using YAML/Go rules. | Yes (`rubric-profiles/<category>`) |
| `cs-04-decide` | Stage 6 (Decide) | Surface the owner-only decision queue on `/decide` for item outcomes and anonymous public edit approvals. | No |
| `cs-05-provenance` | Stage 7 (Credit) | Stamp provenance notes via Go templates, enforce 48-hour/5-day SLAs, and compile clean-room JSON build specs. | Yes (`spec-profiles/<tool-type>`) |
| `cs-06-build` | Stage 8 (Build) | Generate isolated static tool repositories from clean-room specs and worked-example fixtures. | Yes (`calculator`, `checklist`, `validator`, `decision-tree`) |
| `cs-07-verify` | Stage 9 (List, QA split) | Run automated 5-condition checks (offline execution, `connect-src 'self'`, zero tracking, worked examples). | No |
| `cs-08-catalog` | Stage 9 (List, publish) | Publish verified, linked, merged, and retired entries to the `clearedstack.com` catalog. | No |
| `cs-09-monitor` | Stage 10 (Revisit) | Run scheduled ETag, XML, and DOM diff checks on FAR/DFARS/NIST feeds, live tools, linked tools, and parked blockers. | Yes (`federal-register`, `ecfr`, `nist-csrc`, `linked-tool-watch`, `live-catalog`) |
| `cs-10-notify` | New cross-cutting worker | Route approved Portal edits, `needs_subtool` tasks, and fingerprinted errors into `cs-git`, and send owner alerts. | Yes (`internal-git`, `github-mirror`, `webhook-alert`, `portal-sse`) |

## The 14 item states and non-linear moves

An item (`PA-XXXX`) does not always march straight from intake to live. The state machine supports 14 explicit states, including early exits, side-branches, revisit loops, and a fail-closed pause state when a worker encounters an unfamiliar format.

| State | Meaning | Normal next step | Non-linear moves & loops |
|---|---|---|---|
| `discovered` | Candidate URL detected by `cs-01-intake`. | `recorded` | Moves to `rejected` if dead, unreachable, or duplicate. |
| `recorded` | Assigned a `PA-XXXX` ID and deduplicated. | `observed` | Pauses in `needs_subtool` if intake source format is unknown. |
| `observed` | Public pages extracted and raw snapshot sealed. | `scored` or `screened-out` | Pauses in `needs_subtool` if `cs-02-observe` hits an unknown layout. |
| `screened-out` | Failed one of the 5 knockout gates. | Terminal (archived) | Owner override in `cs-04-decide` can return it to `observed`. |
| `scored` | Graded on the 100-point rubric by `cs-03-evaluate`. | `approved` | Owner in `cs-04-decide` can choose `parked`, `linked`, `merged`, or `rejected`. |
| `approved` | Owner chose **Build**; provenance & spec compiled. | `building` | Pauses in `needs_subtool` if `cs-05-provenance` lacks a spec profile. |
| `building` | Static repo generated (`cs-06-build`) and verified (`cs-07-verify`). | `live` | Moves to `parked` if blocked by regulatory ambiguity. |
| `live` | Published in the catalog (`cs-08-catalog`). | Monitored by `cs-09-monitor` | Revisit loop: regulatory drift sends it back to `building`; repeal moves it to `retired`. |
| `parked` | Valid idea deferred for missing data, pending rules, or capacity. | Held in backlog | Revisit loop: `cs-09-monitor` returns it to `observed` when the blocker clears. |
| `linked` | Acceptable free, private tool already exists; linked in catalog. | Monitored by `cs-09-monitor` | Revisit loop: if the external tool breaks or adds tracking, returns to `observed`. |
| `merged` | Scope folded into an existing or planned tool repository. | Catalog note published | Re-opens to `observed` only if the parent tool is retired. |
| `rejected` | Declined with a public rationale in the decision log. | Terminal (archived) | None unless re-submitted as a new candidate after major changes. |
| `retired` | Decommissioned from `live` with historical note retained. | Terminal (archived) | None. |
| `needs_subtool` | **Fail-closed pause** when a worker hits an unknown layout or rule. | Resumes previous worker | `cs-10-notify` opens a task in the owning repo; once `cs-runner` builds the new sub-tool and `cs-store` deploys it, `hub-queue-api` automatically replays the item. |

## How priority lanes flow end-to-end

Every queue lease served by `hub-queue-api` belongs to one of three priority lanes. Workers always drain `urgent` before `normal`, and `normal` before `backfill`, so a single 4 GiB node stays responsive even during large discovery sweeps.

| Priority lane | What enters this lane | End-to-end flow behavior |
|---|---|---|
| `urgent` | Regulatory changes from `cs-09-monitor` affecting `live` tools, owner-approved public edits, and replayed `needs_subtool` items after a sub-tool fix ships. | Preempts all other work at every worker (`cs-01` through `cs-10`) so live catalog fixes and unblocked items finish first. |
| `normal` | Standard single candidates from community submissions or owner research, plus routine scheduled revisit checks. | Processed in FIFO order once the `urgent` lane is empty. |
| `backfill` | Bulk automated web-sweep discoveries and low-urgency historical records. | Runs only when both `urgent` and `normal` queues are clear, preventing bulk sweeps from stalling user-facing updates. |
