ClearedStack runs as a 17-pod platform split across two Kubernetes namespaces: `clearedstack` for the 7-pod control plane and `cs-workers` for the 10 deterministic pipeline workers. Separating the cluster into two namespaces keeps shared infrastructure isolated from worker workloads without the overhead of managing a separate namespace for every single service.

## Two Namespaces at a Glance

Think of `clearedstack` as the city hall and utilities, and `cs-workers` as the ten specialized workshops that process public data.

| Namespace | Purpose | Pods | Typical RAM Requested |
| --- | --- | --- | --- |
| `clearedstack` | Control plane: Portal, queue API, database, internal Git, OCI registry, builder, and app-store reconciler | 7 pods (`clearedstack-web`, `hub-queue-api`, `postgres`, `cs-git`, `cs-registry`, `cs-runner`, `cs-store`) | ~640 MiB |
| `cs-workers` | Deterministic pipeline: intake, observation, evaluation, decisions, provenance, building, verification, catalog, monitoring, and notifications | 10 pods (`cs-01-intake` through `cs-10-notify`), plus on-demand browser Jobs | ~300 MiB |

Only `clearedstack-web` faces the public internet. Visitors can browse the Portal, inspect live queue depths and sanitized errors, and propose edits without signing in, while internal cluster addresses and data stores stay completely behind the scenes.

## Inside the Control Plane (`clearedstack`)

Instead of bundling heavy third-party suites like Forgejo, Harbor, or Argo CD, the `clearedstack` namespace runs seven small, purpose-built services:

| Pod | Role | RAM Requested |
| --- | --- | --- |
| `clearedstack-web` | Serves the public Portal and App Store UI behind the only public Ingress | 128 MiB |
| `hub-queue-api` | Manages worker queues, leases, live SSE updates, and public edit proposals | 48 MiB |
| `postgres` | Stores core pipeline state (`core.*`) and read-only public views (`pub.*`) on a persistent volume | 256 MiB |
| `cs-git` | Hosts bare `.git` repositories on a persistent volume, fires push webhooks, and mirrors code to GitHub | 64 MiB |
| `cs-registry` | Stores container images internally and keeps the last five digests per app for instant rollback | 64 MiB |
| `cs-runner` | Listens for Git pushes and launches Dockerless build Jobs (`ko` for Go, rootless BuildKit for web) | 32 MiB |
| `cs-store` | Watches `cs-git` and `cs-registry`, deploys updates with Kubernetes Server-Side Apply, and reports sanitized health | 48 MiB |

## Inside the Worker Namespace (`cs-workers`)

All ten workers (`cs-01-intake` through `cs-10-notify`) live in `cs-workers` and are 100% deterministic—there is zero AI at runtime. Each worker reads and writes tasks through `hub-queue-api` rather than touching the database directly.

To keep baseline memory tiny, `cs-02-observe` runs as a lightweight Go HTTP pod (~30 MiB) and spawns on-demand headless browser Jobs only when it encounters a JavaScript-heavy website.

## Default-Deny Network Policies

Both namespaces enforce a default-deny network posture. In Kubernetes, a default-deny network policy means every pod is blocked from sending or receiving network traffic unless an explicit allow rule exists.

- **One public door:** Only `clearedstack-web` accepts traffic from the cluster Ingress. Every other pod in both namespaces is cluster-private.
- **No direct database access from workers:** Pods in `cs-workers` can only call `hub-queue-api` over authenticated ServiceAccount HTTP (plus approved outbound public fetches for observation and monitoring). They cannot reach `postgres`, `cs-git`, or `cs-registry` directly.
- **Hidden internals:** Because `cs-store` strips node names, pod hostnames, and internal IPs before forwarding status to `hub-queue-api`, the public Portal never leaks cluster topology.

## Priority Classes

When a single node gets busy—for example, when `cs-runner` compiles a new image or `cs-02-observe` launches a headless browser Job—Kubernetes priority class rules decide which pods keep their resources first.

| Priority Tier | Assigned Workloads | Behavior Under Pressure |
| --- | --- | --- |
| High (Control Plane) | `postgres`, `hub-queue-api`, `clearedstack-web`, `cs-git`, `cs-registry`, `cs-store` | Protected from eviction so the Portal, queues, and storage stay responsive |
| Standard (Workers) | `cs-01-intake` through `cs-10-notify` | Run steadily with predictable small footprints; yield before control-plane pods |
| Low (Ephemeral Jobs) | `cs-runner` build Jobs and on-demand headless browser Jobs | Scheduled when capacity is available and preempted first if memory tightens |

## Non-Root Security Without Docker

Every pod in both `clearedstack` and `cs-workers` runs as an unprivileged non-root user with dropped Linux capabilities, no privilege escalation, and read-only root filesystems wherever state does not need to be written.

There is no Docker daemon anywhere in the cluster. `k3s` runs containers directly through `containerd`, `cs-runner` builds Go binaries with `ko` and web assets with rootless BuildKit, and `cs-store` applies manifests natively without custom CRDs.

## Why It Fits on a Single 4 GiB `k3s` Node

Traditional self-hosted Git, registry, CI, and GitOps stacks easily consume several gigabytes of RAM before a single application runs. By replacing them with clean-room Go microservices, ClearedStack keeps its entire 7-pod control plane around **~640 MiB of requested RAM** (~1.25 GiB limit). Adding all 10 deterministic Go workers (~300 MiB) brings the whole 17-pod platform under 1 GiB of baseline memory—leaving plenty of headroom on a single 4 GiB `k3s` node ($10–$20/month) for ephemeral builds, browser Jobs, and Kubernetes itself.
