Publishing a tool in `clearedstack.com` is not the end of its lifecycle. Federal rules change, external websites break, and visitors propose improvements on the open Portal. Workers `cs-09-monitor` and `cs-10-notify` close those loops. Like every service in the `cs-workers` namespace, both are lightweight, 100% deterministic Go programs with zero AI at runtime, pulling leased work from `hub-queue-api` and producing identical results on any cluster.

## cs-09-monitor: Scheduled Diffs and Reopening Items

`cs-09-monitor` keeps the catalog accurate over time by running scheduled checks against external government sources and already-published entries. Instead of scraping pages blindly, it uses lightweight HTTP ETags (headers that ask a server whether a file has changed since the last check), structured XML feeds, and deterministic DOM (page structure) diffs.

Each source type is handled by a dedicated sub-tool under `tools/<case>/` inside the `cs-09-monitor` repository:

| Sub-tool | What it checks | How it detects change |
|---|---|---|
| `federal-register` | Federal Register notices and rulemakings | Scheduled XML and API diffs for FAR, DFARS, and small-business rule updates. |
| `ecfr` | Electronic Code of Federal Regulations | ETag and XML diffs tracking modified clauses, thresholds, and effective dates. |
| `nist-csrc` | NIST Computer Security Resource Center | Scheduled feed and DOM diffs for cybersecurity standards such as SP 800-171. |
| `linked-tool-watch` | External tools marked `linked` in the catalog | Periodic HTTP and DOM checks for dead links, new paywalls, or added tracking scripts. |
| `live-catalog` | Tools built and published as `live` | Scheduled health and rule-version checks against active ClearedStack tools. |

When a diff confirms a meaningful change, `cs-09-monitor` does not patch tools itself—it reopens the affected `PA-XXXX` item in `hub-queue-api` so the main pipeline handles it deterministically:

- **Reopening `live` items:** If a regulation shifts or a live tool drifts out of date, `cs-09-monitor` places the item in the `urgent` priority lane and routes it back toward `building` for an updated release—or toward `retired` if the underlying rule was repealed.
- **Reopening `parked` items:** Items previously deferred in `parked` because of a pending rule or missing public data are re-checked on schedule. Once the blocker clears, `cs-09-monitor` returns the item to `observed` for a fresh evaluation.
- **Reopening `linked` items:** If an external free tool goes offline or starts tracking users, `cs-09-monitor` moves it back to `observed` so the owner can decide whether to build a clean-room replacement.

## cs-10-notify: Deduplication, Git Routing, and Alerts

`cs-10-notify` is the cross-cutting router that turns worker failures, `needs_subtool` pauses, and owner-approved Portal proposals into clean repository commits, alerts, and live browser updates.

A key job of `cs-10-notify` is **issue deduplication by deterministic fingerprint**. If two hundred queued items hit the exact same unfamiliar HTML table or timed-out endpoint, creating two hundred identical tickets would drown out real problems. Before opening an issue or firing an alert, `cs-10-notify` computes a repeatable fingerprint from the worker name, sanitized error code (such as `E_TIMEOUT` or `E_NEEDS_SUBTOOL`), and failure pattern. If an open issue with that fingerprint already exists in `cs-git`, `cs-10-notify` increments the occurrence count on that existing issue instead of creating noise.

To keep responsibilities cleanly separated, `cs-10-notify` relies on four deterministic sub-tools:

| Sub-tool | Responsibility | Where it writes |
|---|---|---|
| `internal-git` | Commits owner-approved anonymous Portal edits (`DATA`, `CONFIG`, `ISSUE` from `cs-04-decide`), `needs_subtool` tasks, and fingerprinted error issues. | Cluster-private `cs-git` repositories. |
| `github-mirror` | Coordinates outbound code mirroring on change so public contributors can inspect every commit and issue. | Public GitHub mirror (source code only; zero container images). |
| `webhook-alert` | Dispatches concise owner notifications when a genuinely new fingerprinted error, `P0` failure, or `urgent` regulatory shift occurs. | Configured external webhook endpoint. |
| `portal-sse` | Pushes sanitized real-time Server-Sent Events (SSE) through `hub-queue-api` to `clearedstack-web`. | Public Portal UI (`/` Command, `/apps`, `/pipeline`, and live `✎` edit status pills). |

Through `portal-sse`, a visitor who submits an anonymous `✎` edit watches their proposal move live from `Proposed` to `Approved` (in `cs-04-decide`), then `Building` (as `internal-git` commits to `cs-git` and `cs-runner` builds), and finally `Live`—all without signing in or refreshing the page.
