ClearedStack stores all source code and app definitions inside the cluster first, then mirrors code changes outward to GitHub. A small, clean-room Go service called `cs-git` acts as the primary Git server, while GitHub serves strictly as the public code mirror.

## Why cs-git instead of Forgejo

Traditional self-hosted Git platforms like Forgejo bundle a full web interface, user accounts, issue trackers, pull request reviews, and background job queues. ClearedStack does not need any of those features inside its Git server. Public visitors browse status, propose edits, and inspect queues through the `clearedstack.com` Portal without signing in, and the cluster already separates build jobs (`cs-runner`) and deployment (`cs-store`) into focused microservices.

Writing `cs-git` from scratch in Go under the MIT license removes upstream license baggage and shrinks the Git server down to what the cluster actually uses. It runs inside the `clearedstack` control-plane namespace with a 64 MiB memory request and stores bare Git repositories on a Persistent Volume Claim (a dedicated slice of durable cluster disk).

| Capability | Forgejo (Replaced) | cs-git (ClearedStack) |
| --- | --- | --- |
| Primary role | Full web forge with UI and accounts | Headless internal Git server and mirror |
| Codebase and license | Large upstream project | Clean-room Go under MIT |
| Memory footprint | Hundreds of MiB plus database state | 64 MiB RAM requested |
| Storage model | App database plus repository files | Bare repositories on a cluster PVC |
| Cluster integration | General-purpose webhooks | Push webhooks, lightweight patch API, outbound mirror |

## How cs-git acts as primary

Because `cs-git` sits inside the cluster-private `clearedstack` namespace behind a `ClusterIP` service and `NetworkPolicy`, it is unreachable from the public internet. Only `clearedstack-web` exposes a public door. Everything that writes code or configuration inside the platform talks to `cs-git` first:

- **Approved public edits:** When a visitor proposes a change on `clearedstack.com` and the owner approves it in `cs-04-decide`, `cs-10-notify` commits the patch directly to `cs-git`.
- **Missing sub-tool tasks:** When a deterministic worker encounters an unfamiliar page or table layout, it pauses in `needs_subtool` and opens a task in the owning repository in `cs-git`.
- **Image digest updates:** After `cs-runner` builds and tests a new version, it updates the app's `app.yaml` manifest in `cs-git` (tagged `[skip-ci]` so it does not trigger another build loop).

Whenever a commit lands on `main` or a new tag is created, `cs-git` fires two actions: it sends a push webhook to `cs-runner` to start a build, and it automatically pushes the updated code commits to the public GitHub mirror.

## Why container images never touch GitHub

ClearedStack mirrors source code to GitHub so anyone can read, audit, or fork the entire platform, but container images never leave the cluster for GitHub Packages.

| Aspect | GitHub (Public Mirror) | cs-registry (Internal OCI Store) |
| --- | --- | --- |
| What is stored | Source code commits and tags only | Signed OCI v2 container images |
| Network path | Outbound push from cs-git on change | Cluster-private inside clearedstack |
| Rollback speed | Requires external network pull and auth | Instant local pull from last 5 digests |
| Cleanup | External package retention rules | Daily garbage collection on cluster PVC |

Keeping images inside `cs-registry` (a 64 MiB Go service backed by a local PVC) removes external registry credentials from worker pods, keeps cluster-private build artifacts off third-party servers, and guarantees that rollbacks work even if the outside internet is slow or unreachable.
