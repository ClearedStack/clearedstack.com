ClearedStack has no login wall, no waitlist, and no paid tier. Everything running in production and everything being developed is visible to anyone who opens `clearedstack.com`. You can inspect live worker health, watch queues move, read sanitized error codes, and propose edits without creating an account.

This is a deliberate choice: an open public sandbox turns every curious visitor into a potential tester and contributor, while strict technical boundaries keep the underlying host safe.

## Why there is no lock on the site

Most platforms hide their errors, queues, and internal workflows behind login screens or status pages that only say "All systems operational." ClearedStack does the opposite:

- **Zero accounts for visitors:** You never need to sign in or hand over an email address to browse `/apps`, trace `/pipeline`, use `/tools`, or propose an edit using the edit button.
- **MIT-licensed code:** Every repository—from the portal to `cs-git`, `cs-registry`, `cs-runner`, `cs-store`, and all 10 workers (`cs-01` through `cs-10`)—is clean-room Go or web code under the MIT license, mirrored publicly on GitHub.
- **Visible failures:** When a worker hits a snag, it does not silently swallow the problem. It logs a sanitized error code (such as `E_TIMEOUT`, `E_PARSE`, or `E_NEEDS_SUBTOOL`) and surfaces it in the portal.

## How breaking things makes the platform stronger

When visitors test the sandbox, submit unusual URLs, or spot mistakes on a page, they inevitably find edge cases the system has not seen before. Because ClearedStack is 100% deterministic—with zero AI guessing at runtime—every failure becomes a permanent improvement:

1. **Fail closed, not silent:** If `cs-02-observe` or another worker encounters an unfamiliar page layout, it pauses that item in `needs_subtool` and opens a task in the owning repository.
2. **Build a deterministic sub-tool:** A small, targeted sub-tool and golden test fixture are added to handle that exact pattern.
3. **Automatic replay:** Once `cs-runner` tests and builds the update and `cs-store` deploys it, `hub-queue-api` automatically replays the paused items. Every edge case a visitor triggers turns into permanent, repeatable code.

## Anonymous edits with a 5-layer safety shield

Letting anyone propose a change without signing in would normally invite spam bots. ClearedStack stops abuse without forcing humans through logins or third-party CAPTCHAs by using five deterministic checks:

1. **Browser Proof-of-Work:** Submitting an edit runs a quick (~1 second) cryptographic puzzle in your browser, making bulk bot spam expensive.
2. **Honeypot field:** A hidden form field invisible to humans catches automated scrapers and silently drops their submissions.
3. **Daily-salted IP hash rate limit:** The server caps submissions per hashed IP using a salt that rotates daily, so raw visitor IP addresses are never stored.
4. **Strict schema validation:** Every proposal is checked against `ownership_map.json`, limited to 4 KB, restricted to allowed edit classes (`DATA`, `CONFIG`, or `ISSUE`), and stripped of HTML or scripts.
5. **Human review gate:** Proposals sit in a pending queue and never touch `cs-git` or the cluster until reviewed and approved in `/decide` (`cs-04-decide`).

While waiting, your edit button updates live in place so you can watch your contribution move from **Proposed** to **Approved**, **Building**, and **Live**.

## How isolation and rollbacks protect the host

Open visibility does not mean exposing the server's internals or letting bad updates take down the host. Strict separation keeps the cluster healthy even under heavy public use:

| 100% Public (Portal & GitHub) | Cluster-Private (Hidden & Isolated) |
| --- | --- |
| All MIT source code, pipeline rules, rubric weights, and sub-tools | Internal cluster IPs, node names, pod hostnames, and internal DNS |
| Live app and worker health, queue depths, and item trails | Network policy rules and Ingress internals |
| Sanitized error codes (`E_TIMEOUT`, `E_PARSE`, `E_NEEDS_SUBTOOL`) | Database passwords, ServiceAccount tokens, signing keys, and daily IP salts |
| Read-only `pub.*` database views | Raw captured web snapshots behind the clean-room wall |

Four structural guardrails enforce this boundary:

- **Single public door:** Only `clearedstack-web` has a public Ingress. The control plane and workers cannot be reached directly from the internet.
- **Two-namespace isolation:** The control plane runs in the `clearedstack` namespace, while all 10 workers run in `cs-workers`, separated by Kubernetes network policy rules.
- **Metadata stripping:** `cs-store` strips node names, pod hostnames, and internal IPs before sending any status or error to the portal.
- **Instant 1-click rollbacks:** `cs-registry` keeps the last five signed image digests for every app. If a new build misbehaves, `cs-store` restores the previous working version immediately.
