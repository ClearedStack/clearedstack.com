Most documentation sites ask you to read thousands of words of prose before you ever see software do anything. Folks are done reading. ClearedStack v3.1 pairs the contractor-first catalog at `/tools/` with a live operational window inside `/guides/`—opening directly into the cluster running the software factory.

Instead of only reading about how the system is supposed to work, you can open `/guides/command/`, `/guides/apps/`, `/guides/pipeline/`, or `/guides/decide/` and inspect live state: which apps are healthy, which workers are busy, what is waiting in a queue, and what paused.

## From static essays to live factory views under Guides

Earlier versions of the site explained the architecture solely through long-form guides. In v3.1, all operational views live side-by-side with the Section L manual under `/guides/`, powered by `hub-queue-api` and `cs-store`:

- **Live status over static claims:** Every worker and app reports real health, version, and queue depth straight from the cluster.
- **Short explanations in context:** Instead of forcing you out of context, each live view uses compact `[? Why]` drawers right next to rules and metrics so you can inspect the rationale in seconds.
- **100% deterministic behavior:** There is no AI running in the portal or in any of the 10 workers (`cs-01` through `cs-10`). Every status badge, queue transition, and priority ranking follows fixed, predictable rules.

## How software rules promote what matters

A live dashboard is useless if healthy background noise buries a real outage. On [Command](/guides/command/), deterministic priority rules automatically sort what appears at the top of the screen:

| Priority | What triggers it | How the portal displays it |
| --- | --- | --- |
| **P0 (Critical)** | An app or worker is down, crashing, or reporting an active error code | Promoted to the top in crimson (`AttentionCard`) with the sanitized error code and affected component |
| **P1 (Stalled)** | A worker queue is backed up, a job timed out, or an item is paused in `needs_subtool` | Surfaced alongside P0 items in amber so bottlenecks are obvious immediately |
| **P2 (Pending)** | Items waiting in `cs-04-decide` or public edit proposals waiting for owner review | Listed as actionable pending work ready for a decision in `/guides/decide/` |
| **Quiet / Idle** | Healthy workers with empty queues and no errors | Kept calm and muted so idle infrastructure stays out of your way |

Because these rules are pure code rather than guesswork, the same cluster state always produces the exact same view.

## One control plane, one lifecycle

Behind the scenes, the portal connects two halves of the platform without mixing them up:

1. **Software delivery (`/guides/apps/` & `/tools/#apps`):** `cs-git` stores the code, `cs-runner` builds container images without Docker (using `ko` for Go and rootless BuildKit for web apps) and pushes them to `cs-registry`, and `cs-store` applies those apps to Kubernetes and streams sanitized health back to the App Store.
2. **Data and tool production (`/guides/pipeline/`, `/guides/decide/`, `/tools/`):** The 10 deterministic workers pull tasks from `hub-queue-api`, process public sources, pause for human judgment at `/guides/decide/`, and publish verified browser tools to `/tools/`.

Every piece you see in the portal is backed by open-source code mirrored to GitHub, so what you see running on `clearedstack.com` is the exact system you can inspect or host yourself.
