ClearedStack is an open, MIT-licensed platform built from clean-room code. Everything runs in the open across the web Portal (`clearedstack.com`), four lightweight control-plane services (`cs-git`, `cs-registry`, `cs-runner`, `cs-store`), and ten deterministic worker repositories (`cs-01-intake` through `cs-10-notify`).

There are two ways to contribute: propose a change directly on the live Portal without creating an account, or work in the MIT clean-room repositories to add guides, catalog entries, or deterministic sub-tools.

## Two ways to contribute

| Path | Best for | Login needed? | How it goes live |
| :--- | :--- | :--- | :--- |
| **Live Portal edit button** | Fixing text, correcting catalog data, or flagging an issue | No | Passes anti-spam checks, waits for owner approval in `cs-04-decide`, then flows into `cs-git` |
| **MIT clean-room repositories** | Adding guides, building Portal features, or writing new worker sub-tools (`tools/<case>/`) | GitHub account for pull requests | Tested with golden fixtures, built without Docker by `cs-runner`, and deployed by `cs-store` |

## 1. Edit directly on the live Portal (no login)

Anyone visiting `clearedstack.com` can inspect what is running, view sanitized errors, and propose changes using the edit button (`✎`) shown on the Portal. You do not need an account, password, or local setup.

Because the edit button is open to the public, every submission passes through a five-layer safety shield before it can touch the codebase:

| Layer | What it does |
| :--- | :--- |
| **Browser Proof-of-Work** | Runs a quick puzzle in your browser on submit to stop automated bots without using CAPTCHAs |
| **Honeypot field** | A hidden form field that silently discards automated scraper submissions |
| **Daily-salted IP hash** | Limits repeated submissions from the same source without ever storing raw IP addresses |
| **Schema and size check** | Validates the target against `ownership_map.json`, caps edits at 4 KB, and strips any HTML or scripts |
| **Human approval gate** | Holds every proposal in `cs-04-decide` until the site owner clicks **Approve** |

Once you submit an edit, the `✎` button turns into a live status pill that tracks your proposal from **Proposed** to **Approved**, **Building**, and **Live**.

## 2. Work on the MIT clean-room repositories

All ClearedStack repositories are released under the **MIT License** and written from scratch as clean-room Go and TypeScript code, with zero copied upstream code and zero AI at runtime.

Inside the cluster, `cs-git` is the primary Git server. Whenever changes land on `main` or a tag, `cs-git` automatically pushes a **public code mirror to GitHub**. GitHub is a code mirror only—zero container images are stored or served from GitHub.

| Repository group | What it holds | Typical contributions |
| :--- | :--- | :--- |
| **`clearedstack.com`** | Next.js, TypeScript, and Tailwind CSS Portal, tool catalog (`src/data/catalog.ts`), and guides (`src/guides/`) | Writing or updating guides, adding catalog entries, improving Portal UI |
| **Control plane** (`cs-git`, `cs-registry`, `cs-runner`, `cs-store`) | Clean-room Go services for Git mirroring, internal OCI storage, Dockerless builds, and Kubernetes app deployment | Fixing bugs, tightening guardrails, improving build or deploy reliability |
| **10 Worker repos** (`cs-01-intake` .. `cs-10-notify`) | Deterministic Go pipelines for intake, observation, evaluation, decisions, provenance, building, verification, cataloging, monitoring, and notifications | Adding deterministic sub-tools (`tools/<case>/`) and golden fixtures |

## Adding deterministic sub-tools and golden fixtures

Every worker runs with **100% deterministic logic**—there are no language models, no guesswork, and no hidden network calls at runtime. When a worker encounters an unfamiliar page layout, document format, or edge case, it **fails closed**: it pauses the item in a `needs_subtool` state and opens a task in the owning worker repository.

Contributors solve these edge cases permanently by adding a deterministic sub-tool inside the worker repository:

1. Create a new folder under `tools/<case>/` and register it in `tools/registry.yaml`.
2. Add the matching rules and deterministic Go extraction or evaluation logic for that specific case.
3. Add **golden fixtures** in `fixtures/`—saved sample inputs paired with the exact expected JSON output—so the behavior is locked in and repeatable on every run.

When a sub-tool and its golden fixtures are merged into `cs-git`, `cs-runner` runs the golden test suite, builds the updated worker image, and `cs-store` deploys it. The queue service (`hub-queue-api`) then automatically replays all paused `needs_subtool` items that match the new pattern.

## How builds work (zero Docker anywhere)

ClearedStack uses **zero Docker anywhere**—not on contributor machines and not in cluster builds. Images are built directly from source using lightweight, rootless tools and stored in the internal `cs-registry` before running on `k3s` with `containerd`.

| Component | Build tool | Where the image lives | Runtime |
| :--- | :--- | :--- | :--- |
| **Go workers & control-plane services** | `ko` | Internal `cs-registry` | `k3s` + `containerd` |
| **Next.js Portal (`clearedstack.com`)** | Rootless BuildKit | Internal `cs-registry` | `k3s` + `containerd` |

## Rules for every contribution

- **MIT and clean-room only:** Write original code and documentation; never copy code from upstream projects or other licenses.
- **Zero AI at runtime:** Workers and shipped tools must produce the exact same output every time for the same input.
- **Zero tracking or external assets:** The Portal loads nothing from third-party servers and sets no tracking cookies.
- **Public data only:** Never include classified information, CUI, export-controlled data, or real contract figures in code, fixtures, guides, or commit messages.
