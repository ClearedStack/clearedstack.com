Because ClearedStack runs 100% deterministic workers with zero AI at runtime, a worker never guesses when it hits something unexpected. Instead, it stops cleanly, reports what happened in plain terms, and protects both your data and your cluster internals. Understanding how the pieces fit together turns a red status card from a guessing game into a predictable five-step loop.

## 1. Live Error Reporting Without Exposing Cluster Internals

When a worker pod in the `cs-workers` namespace stalls, crashes, or fails a job, `cs-store` notices immediately. It watches pod, deployment, and Kubernetes event health across the cluster and strips out all private infrastructure details—such as internal IP addresses, node names, pod hostnames, and cluster DNS names—before forwarding a sanitized status update to `hub-queue-api`.

From there, `hub-queue-api` updates the read-only `pub.*` database views and pushes live updates over Server-Sent Events (SSE) to the Portal. On Command (`/guides/#command`), urgent `P0` errors and `P1` stalled queues float straight to the top while healthy, idle workers stay collapsed. On Apps (`/tools/#apps`), the affected worker card turns red and displays its active error code. Because the Portal is an open public sandbox with no login wall, anyone can inspect live worker health and sanitized errors without ever seeing credentials or private network topology.

## 2. Sanitized Error Codes

Every public error is mapped to a short, sanitized code so you know *why* a worker stopped without reading raw stack traces or leaking internal paths.

| Error Code | What It Means in Plain Language | What Happens Next |
| --- | --- | --- |
| `E_TIMEOUT` | A worker waited too long for an external website, PDF download, or internal step to respond. | The item stays safe in the queue and can be retried without losing earlier progress. |
| `E_PARSE` | A worker received data that broke its expected format, such as malformed JSON or a corrupted file. | The worker refuses to guess, logs the sanitized failure, and halts that item cleanly. |
| `E_NEEDS_SUBTOOL` | A worker saw a valid but unfamiliar layout, such as a new government table structure it has no rule for yet. | The worker fails closed, pauses the item in `needs_subtool`, and requests a new deterministic sub-tool. |

When an item lands in `needs_subtool`, nothing is lost. Once a developer or owner adds a new deterministic sub-tool and golden test fixture to that worker's repository, `cs-runner` tests and builds the updated image, `cs-store` deploys it, and `hub-queue-api` automatically replays all paused items matching that pattern.

## 3. Worker Local Spools

Sometimes the problem is not the data—it is a brief hiccup between a worker and `hub-queue-api`, such as a control-plane restart or a momentary network blip. Each worker keeps a local spool, which is a small on-disk holding queue inside the worker pod.

If `hub-queue-api` is temporarily unreachable when a worker finishes a job or needs to report an error, the worker writes the result to its local spool instead of dropping it on the floor. As soon as the connection recovers, the worker flushes its spooled updates in order. Because every worker is deterministic, replaying or flushing spooled work produces the exact same outcome.

## 4. 1-Click Pause and Rollback in `/tools/#apps`

If a worker turns red right after an update—or keeps hammering a broken external site—you do not need to edit cluster manifests by hand. In Owner Mode on `/tools/#apps`, `cs-store` gives you two immediate safety switches on every worker card:

| Action | What It Does | When to Use It |
| --- | --- | --- |
| **Pause** | Uses built-in Kubernetes Server-Side Apply to halt the worker cleanly without deleting its queues or configuration. | Use when an external target is down or you want to stop retries while investigating. |
| **Rollback** | Switches the worker back to a previous signed image digest stored locally in `cs-registry` (which keeps the last 5 digests per app). | Use when a newly built worker version introduced a regression and you want a known-good build back in seconds. |

Because `cs-registry` holds recent signed digests inside the cluster, Rollback works without pulling anything from GitHub or running Docker.

## 5. Automatic Issue Deduplication in `cs-10-notify`

If 200 queued items hit the exact same unfamiliar table layout or timed-out endpoint, you do not want 200 identical bug reports flooding your inbox. Before any alert or repository task is created, `cs-10-notify` computes a deterministic fingerprint from the worker name, sanitized error code, and failure pattern.

If an open issue with that fingerprint already exists in `cs-git` (which mirrors code and tasks to GitHub on change), `cs-10-notify` updates the existing issue count instead of opening a duplicate. Only genuinely new failure patterns create new issues or trigger fresh owner alerts, keeping troubleshooting focused on root causes rather than noise.
