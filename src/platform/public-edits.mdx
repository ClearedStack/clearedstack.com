## Why there is no lock

Most projects hide their queues and their errors behind a sign-in, or a status page that says everything is fine. This design does the opposite, for a practical reason: every curious reader is a possible tester. When a reader finds a case the pipeline has no rule for, that case becomes a tested rule, and the system is better for it. See [Sub-tools](/platform/pipeline/#sub-tools-one-rule-for-each-case).

## Proposing an edit

Anything a reader might want to correct carries a small Edit button: a description, a setting, a rule. Pressing it opens a form showing what the element holds now, with room for the proposed change and the reason.

The reader does not need to know which repository owns what. A public file in the hub repository, `ownership_map.json`, records for every editable element which repository it belongs to, which file, and what kind of change it is.

| Kind of edit | What it changes | What happens once the owner approves |
| --- | --- | --- |
| `DATA` | Catalog text, a description, a record | The record is updated and the change is logged |
| `CONFIG` | A worker’s settings, a scoring weight, a rule’s options | A change is committed to the owning repository, tested, built and deployed |
| `ISSUE` | A report of something broken, or a request for a missing rule | One task is opened in the owning repository, or added to an existing one for the same problem |

## Five checks instead of a login

Accepting proposals from anyone on the internet invites automated abuse. The design stops it without accounts and without an outside CAPTCHA service.

| Check | How it works | What it costs a real reader |
| --- | --- | --- |
| 1. Proof of work | On submit, the browser solves a small puzzle that takes about a second | Nothing noticeable. For a bot sending thousands, it is expensive |
| 2. Honeypot | A field no person can see. Anything that fills it in is discarded | Nothing |
| 3. Rate limit | Submissions are capped for each source address, using a one-way hash made with a secret that changes daily | Nothing. The address itself is never stored |
| 4. Shape and size | The target must exist in `ownership_map.json`, the proposal must be under 4 KB, and all markup and scripts are stripped | A long proposal has to be split |
| 5. A person | Every proposal waits until the owner approves it | A wait |

The fifth is the one that matters most. No proposal can reach a repository or the cluster by itself.

## What is public and what is private

Being open about how the project works does not mean publishing a map of the machine it runs on. The rule is: hide the network, show the logic.

| Public | Private |
| --- | --- |
| All source code, under the MIT license | Addresses, host names and names inside the cluster |
| Every rule, scoring weight and tie-breaker | Network rules and the layout of the cluster |
| Every sub-tool and its test examples | Database passwords, tokens and signing keys |
| Health of each component, queue lengths and each item’s history | The secret used to hash visitor addresses |
| Error codes such as `E_TIMEOUT`, `E_PARSE` and `E_NEEDS_SUBTOOL` | Visitor addresses, which are never stored |
| Proposals and their status | The raw pages captured during observation |

Four things in the design hold that line.

- **One door.** Only the website can be reached from outside. The queue service, the database, the Git server, the registry and the workers have private addresses only.
- **Two namespaces.** The control plane and the workers are separated, and each blocks traffic that is not explicitly allowed.
- **Views, not tables.** The website reads the database through a restricted role that can see only views built for publication. A private column cannot appear on a page, because the website is never given it.
- **Errors are cleaned first.** When something fails, the event Kubernetes produces often names a machine or an address. Shipkeeper removes those and maps the failure to one of the public error codes before anything is reported. A reader sees what broke and at which stage, not where.

If a bad change does get through, the previous version is one step away: the last five signed images of every component are kept, and a rollback needs nothing from outside. See [Cluster architecture](/platform/cluster-architecture/#install-upgrade-pause-roll-back).

## What never to put in a proposal

A proposal is public by design. Do not include classified information, controlled unclassified information, export-controlled data, real contract figures or anything that identifies a real company’s bid. The same rule applies to an issue or an email. See [What never goes in](/guides/request-or-add-a-tool/#what-never-goes-in).
