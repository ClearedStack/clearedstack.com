Every idea for a tool is an item with an identifier of the form `PA-0001` and exactly one state. This page lists the fourteen states, shows which worker moves an item from one to the next, and explains the order in which waiting items are taken.

## The fourteen states

An item does not always go straight from found to live. It can leave early, wait for something outside the project, or come back after it was finished.

## Which worker makes each move

| State | What it means | Usually goes to | Other moves |
| --- | --- | --- | --- |
| `discovered` | `cs-01-intake` has seen a candidate | `recorded` | `rejected` if the address is dead or a duplicate |
| `recorded` | It has an identifier | `observed` | `needs_subtool` if the source is in a form intake has no rule for |
| `observed` | `cs-02-observe` has read its public pages | `scored` or `screened-out` | `needs_subtool` if the page layout is unfamiliar |
| `screened-out` | `cs-03-evaluate` found it fails a gate | Stays there | The owner can send it back to `observed` |
| `scored` | `cs-03-evaluate` has rated it | `approved` | The owner can choose `parked`, `linked`, `merged` or `rejected` |
| `approved` | The owner chose to build, and `cs-05-provenance` wrote the specification | `building` | `needs_subtool` if there is no profile for that kind of tool |
| `building` | `cs-06-build` generated it and `cs-07-verify` is checking it | `live` | `parked` if the rule turns out to be unclear |
| `live` | `cs-08-catalog` published it | Watched by `cs-09-monitor` | Back to `building` when the rule changes, or `retired` when it is repealed |
| `parked` | A good idea that is blocked | Stays there | Back to `observed` when `cs-09-monitor` sees the blocker clear |
| `linked` | The catalog points at an existing tool | Watched by `cs-09-monitor` | Back to `observed` if that tool breaks or starts tracking users |
| `merged` | Folded into another tool | Stays there | Back to `observed` only if the other tool is retired |
| `rejected` | Declined, with the reason public | Stays there | None, unless it is sent in again as a new candidate |
| `retired` | Removed from use, with a note | Stays there | None |
| `needs_subtool` | A worker stopped instead of guessing | Back to the worker that paused it | Runs again automatically once the missing rule ships |

The three catalog labels a reader sees come from these states: `approved` shows as Planned, `building` as In development and `live` as Live.

## Three priority lanes

Every waiting item is in one of three lanes. Each worker empties the urgent lane before it touches the normal one, and the normal one before backfill. That keeps a small machine responsive while a large sweep is running.

| Lane | What goes in it | How it is handled |
| --- | --- | --- |
| `urgent` | A change in a regulation that affects a live tool, an edit the owner has approved, and items being run again after a missing rule shipped | Taken first at every worker, so fixes to live tools finish before anything else |
| `normal` | Single candidates from requests or the owner’s own research, and routine scheduled checks | Taken in the order they arrived, once the urgent lane is empty |
| `backfill` | Bulk finds from automated sweeps, and old records | Taken only when both other lanes are empty |

## What does not get lost

Two things protect work in progress. An item a worker has claimed goes back in the queue if that worker stops, because its lease runs out. And a result a worker has finished is kept on the worker’s own disk until the queue service confirms it has it, so a restart in the middle loses nothing. [Cluster architecture](/platform/cluster-architecture/#one-database-and-one-gatekeeper) describes both.
